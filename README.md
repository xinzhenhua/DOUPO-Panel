# 豆粕基本面自动预警仪表盘

## 这是什么

一个网页仪表盘，用来每天快速查看豆粕基本面情绪：

| 板块 | 自动化程度 | 数据源 |
|---|---|---|
| 🌦️ 天气预报 | 🟢 完全自动，打开网页实时抓取 | Open-Meteo（免费，确认支持浏览器CORS） |
| 🏜️ 官方干旱监测(现状) | 🟢 自动，每天2次由GitHub Actions同步 | US Drought Monitor官方API，覆盖12个大豆主产州（NDMC/USDA/NOAA） |
| 📅 NOAA月度干旱展望(未来1个月) | 🟢 自动，每天2次由GitHub Actions同步 | NOAA/CPC官方ArcGIS服务，12州×每州8点采样统计百分比（专家研判，综合ENSO等因素） |
| 🌱 美豆优良率 | 🟢 自动，每天2次由GitHub Actions同步（仅4-11月生长季有数据） | USDA/NASS周度作物生长报告(Crop Progress) |
| 💰 人民币汇率 | 🟢 完全自动，打开网页实时抓取 | Frankfurter/ECB（免费，确认支持浏览器CORS） |

## 移动端触控体验优化

对照iOS/Android官方建议的最小点击目标(约44px)重新核实过一遍界面上的可点击元素，
发现几个明显偏小的地方并修正：
- 合约切换按钮(9月/5月/1月)：原本高度不到40px，现在补到44px
- "采用"按钮(粘贴解析结果里的单项采用按钮)：原本字体9px、几乎没有内边距，
  现在放大到接近正常按钮的尺寸
- 折叠区块的展开/收起标题栏：原本偏小，现在加大了内边距
- 手动输入框：字体和内边距都略微加大，输入数字时更舒适

SVG图表(条形图/仪表盘)本来就用`width:100%`配合`viewBox`做响应式缩放，
窄屏幕下不会有横向滚动或图表挤在一起看不清的问题，这块没有改动。

查了美国大豆种植面积官方数据(SoyStats，美国大豆协会官方年鉴，2024年数据)精确算过占比：

```
核心8州(伊利诺伊/爱荷华/明尼苏达/印第安纳/内布拉斯加/俄亥俄/密苏里/南达科他)
= 全国种植面积64.0%

加上次要4州(北达科他/堪萨斯/密歇根/威斯康星)
合计12州 = 全国种植面积81.8%
```

天气/干旱监测/NOAA展望三个板块都覆盖这12州，逐州明细收进"查看详情 ▸"里点开才看。

**关于"平均"的计算方式**：一开始12州是简单平均(每个州权重相等)，但这样不合理——
伊利诺伊(全国最大产区)天气不好，跟南达科他(小得多的产区)天气不好，
对全国供给的实际影响显然不一样，不该被简单平均"各打五十大板"。

现在改成**按种植面积加权平均**：用上面SoyStats的官方种植面积数据做权重，
伊利诺伊/爱荷华这些大产区的天气/干旱状况会占更大权重。界面上会同时显示
加权平均和简单平均两个数字，方便对比看出差异有多大。这个逻辑同时应用在
天气(纯前端计算)、干旱监测、NOAA月度展望这三处，权重数据两边(前端JS和
后端Python)保持完全一致。

## 为什么放弃了"AI自动搜索"这几个指标

最早尝试过让脚本自动调用AI(Groq+Tavily)去联网搜索这几个指标，但实测发现真正的问题
不是"AI不够聪明"，而是这几个数据背后是付费商业数据源(汇易/mysteel等)，
公开网络上搜到的要么是过期数据，要么AI会把不相关的数字(比如价格表格)
误判成目标指标——换哪家AI都是同样的根本限制，因为AI只能从搜到的内容里提取。

现在改成更可靠的方式：**你自己去问AI(用哪家都行) → 人眼确认答案靠谱 → 粘贴回来给本地解析**。
这样"判断数据是否可信"这一步交给了你自己（而不是脚本自动信任AI的输出），
本地解析只做纯文本正则匹配，不联网、不调用任何AI，出错了也是"没识别到"而不是"静默填错"。

## 为什么有的自动有的手动

网页本身（浏览器里跑的JS）受"跨域限制(CORS)"约束，不能直接访问大部分外部网站。
天气数据源（Open-Meteo）恰好支持浏览器直接调用，所以能做到真正实时。

USDA的数据虽然有官方API，但和CBOT价格一样，不适合在浏览器里直接暴露API密钥，
所以采用"GitHub Actions服务器端定时抓取 → 写入json文件 → 网页读取json"的方案。
这个json文件和网页在同一个域名下（同源），读取不受CORS限制。

中国海关/农业农村部/汇易咨询等网站没有公开API，也没有好的官方替代数据源，
所以改用"你复制提示词去问AI → 把AI的回答粘贴回来 → 本地解析填充"这套流程，
你随时可以手动覆盖解析出来的数值。

## 快速开始

### 第一步：立即可用（0配置）
直接打开 `index.html`，天气板块、汇率板块和手动录入板块马上能用。

### 第二步：开启USDA/CBOT自动同步（约15分钟，一次性）

1. **申请免费API密钥**
   打开 https://api.data.gov/signup/ ，填邮箱，几秒钟收到密钥邮件

2. **新建GitHub仓库**
   把这个文件夹的全部内容上传到一个新仓库（public或private都可以）

3. **添加密钥到仓库Secrets**
   仓库页面 → Settings → Secrets and variables → Actions
   → New repository secret
   → Name: `USDA_API_KEY`，Value: 粘贴你申请到的密钥

4. **开启GitHub Pages**
   仓库页面 → Settings → Pages
   → Source 选择 "Deploy from a branch" → Branch选 `main` → Save
   → 几分钟后会生成 `https://你的用户名.github.io/仓库名/`

5. **手动触发第一次运行**
   仓库页面 → Actions标签 → 左侧选"更新豆粕基本面数据"
   → 右上角 "Run workflow" → 点击运行
   → 等待约1分钟，跑完后 `data/latest.json` 会被自动更新并提交

6. **之后完全自动**
   豆粕交易时段内每小时自动运行一次(日盘9:00-15:00、夜盘21:00-23:00，各挑整点
   后5分钟触发，一天9次)，无需人工干预。2026-09更新：之前是一天固定2次，
   仓库确认是公开的(GitHub Actions对公开仓库完全免费、不限分钟数)之后改成这个
   频率，之所以不选更高频率(比如GitHub允许的5分钟一次下限)，是因为豆粕的K线
   最细颗粒度是小时线，且新浪财经/东方财富这类接口过于频繁请求有触发反爬风控
   的风险(参考龙虎榜那次BadZipFile的教训)，每小时一次是"够用又不浪费"的
   平衡点。具体排程见`.github/workflows/update-data.yml`里的注释。

### 第三步：美豆优良率（USDA每周作物生长报告）

1. 打开 https://quickstats.nass.usda.gov/api → 免费申请密钥（跟USDA_API_KEY是两套不同系统，NASS单独一套）
2. 添加Secret：Name: `NASS_API_KEY`，Value: 你的密钥
3. 这个指标只在每年4月-11月生长季有数据，其余月份显示"暂无数据"属正常现象

### 第四步：开机率/库存/基差/到港预报/猪粮比/能繁母猪/进口量/肉鸡养殖利润/豆菜粕价差 —— 复制提示词→粘贴解析

这7个指标背后是商业数据服务或政府网页表格，没有公开API，改用最简单可靠的方式：

1. 打开网页，找到"📋 一键复制提示词 → 粘贴填充"这个板块
2. 点击"复制提示词"，粘贴到你信任的任意AI对话框（DeepSeek/豆包/通义千问/ChatGPT都行）
3. 看一眼AI给出的表格，确认数据看起来合理（日期新不新鲜、数字量级对不对）
4. 把AI的完整回答复制粘贴回网页的文本框
5. 点击"解析并填充"，系统会自动识别每一行对应哪个指标，提取数值/日期/来源并填入

全程本地解析，不联网、不调用任何AI服务，识别不了的字段会保持原值，
不会出现"看起来自动、实际填错"的情况——判断数据是否可信这一步始终由你自己把关。

## 文件说明

```

fetch_data.py                       ← 数据抓取脚本（GitHub Actions里跑）
test_fetch_data.py                  ← 解析逻辑的单元测试（用模拟数据验证）
data/latest.json                    ← 抓取结果存放处（网页读取这个文件）
.github/workflows/update-data.yml   ← 定时任务配置
```

**修了一个方法论问题**：天气/干旱监测/NOAA展望/美豆优良率这4个指标本质上都在测
"这个生长季天气好不好"，只是时间尺度不同(7天/现在/1个月/本周报告)。之前各自独立
投票，如果真的发生干旱，这4个可能同时转向同一方向，相当于同一件事在总分里被计了
4次票。现在改成：先算这4个子信号的平均态度(≥0.5记为偏多，≤-0.5记为偏空，否则中性)，
合成1个"作物生长状况"综合信号，只投1票——总票数也因此从14变成11(7个供应+4个需求)。
供需表格里显示的是合并后的这1格，展开"查看每项详细理由"能看到4个子信号各自的原始数值。


手写SVG图表（不依赖任何外部图表库，纯手写，加载快）：
- **综合预警仪表盘**：半圆指针，一眼看出当前偏多/偏空/中性，比读文字直观
- **12州对比条形图**（干旱监测/NOAA展望/天气板块都有）：条的长度=数值，
  条的粗细=种植面积权重，直接可视化"为什么加权平均会偏向某个方向"

**综合基本面预警放在了页面最顶端**——打开网页第一眼就看到结论，不用往下翻。
之前试过一个"7指标状态点图"，实际做出来效果不好，已经移除。改成了**供需二栏表格**：
左列是供应侧指标(天气/干旱监测/NOAA展望/美豆优良率/库存消费比/开机率/商业库存/
到港预报/进口量/人民币汇率)，右列是需求侧指标(出口销售/现货基差/猪粮比/能繁母猪)，
每格根据信号变红(偏多)/绿(偏空)/灰(中性)，一眼扫过去看红绿比例就知道整体倾向。
详细的文字理由收进了"查看每项详细理由"这个折叠区块里，不占默认视图空间。

**修了一个真实的时序bug**：之前`loadWeather()`和`loadFxRate()`各自异步拉取数据、
设置好信号变量后，从来没有触发综合预警重新计算——除非用户之后手动改了某个输入框
才会连带刷新。这导致天气和汇率这两个信号实际上经常没有真正体现在最终的预警结果里。
现在这两个函数在数据到达后会主动触发一次重新计算。

首页开头的"首次使用？点击查看部署说明"面板已移除（内容跟README重复，直接看这份
文档更清楚），部署步骤请参考下面的"快速开始"部分。


除了"复制提示词→粘贴填充"这个手动模块，**其他所有板块都只常驻显示一个彩色结论框
(alert-box，带关键数字的简要概况)**，逐州/逐项的详细数据全部收进"查看详情 ▸"里，
点开才看，避免一屏塞太多数字，手机上尤其重要。

手动模块本身也分成了2个大折叠：
- "第一步+第二步：复制提示词→粘贴解析"（不用的时候收起来）
- "手动指标字段"（7个具体指标输入框，同样默认收起）

顺带修了两个之前一直没做多做空结论的板块：
- **供需库存(PSD)**：库存消费比其实一直有算，但没用醒目样式展示结论，现在补上了
- **CBOT期货价格**：之前完全没有结论展示，而且底层信号方向是反的(涨的时候
  算成偏空)，现在修正方向并展示，但明确标注"仅供参考，不计入综合评分"——
  因为CBOT国际基准和国内价格的相关性没有像其他指标那样验证过，
  展示出来供参考，但不掺进最终的综合评分里，避免拉低整体判断的可靠性。

**新增了需求侧指标：白羽肉鸡养殖利润(元/只)**——之前需求侧只覆盖了"猪"
(猪粮比+能繁母猪)，完全没有"禽类"这块。查了官方/行业数据确认阈值：
盈利>1.5元/只(参考真实历史数据0.71-1.73元/只区间)→扩产意愿强→偏多；
亏损(<0元/只，比如查到的真实案例"一只鸡跌去4块钱")→减产退出→偏空。
跟猪粮比逻辑一致：利润驱动养殖户扩产/减产决策，从而影响饲料(豆粕)需求。

**再新增一个需求侧指标：豆菜粕价差(元/吨)**——同时解决了"水产养殖"和
"替代品价格"这两块缺口。查证发现菜粕一半以上用在水产饲料，所以水产
旺季会先带动菜粕供需趋紧，间接体现在豆菜粕价差上，不需要单独做水产指标。
阈值参考多个独立来源+2026年实际数据(4月国内现货价差470-780元/吨)：
<400元/吨(菜粕不够便宜)→豆粕需求锁定→偏多；>700元/吨(菜粕明显划算)→
替代风险上升→偏空。

**综合评分现在是13票制**（14票→天气类4指标合并成1票后变11票→
新增肉鸡指标变12票→新增豆菜粕价差变13票）：
天气类综合/供需库存/开机率/商业库存/到港预报/进口量/人民币汇率(供应侧7项)+
出口销售/现货基差/猪粮比/能繁母猪/肉鸡养殖利润/豆菜粕价差(需求侧6项)，
全部正确计入综合评分，只有CBOT价格是刻意排除、仅供参考的例外。

顺带修了一个之前就存在的小问题：之前"中性"结果不会被记录成理由文字，
如果凑巧填的字段全部落在中性区间，会被误判成"数据不足"（其实数据填了，
只是都没有明确偏向）。现在中性结果也会正常显示理由。

## 三个主力合约切换：9月/5月/1月

**修了1月合约的一个不一致**：之前1月合约的说明文字里写着"南美早期播种"值得关注，
但实际代码把南美数据(group-sa)整个隐藏了——说了但没做。现在1月合约会显示南美
天气+产量数据(南美"播种生长期"跟1月合约建议交易窗口高度重叠)，也会计入综合评分。

**1月合约新增了1个专属指标**：
- **美豆收获进度**：复用同一套NASS基础设施(跟播种进度用的是同一个API，只是
  statisticcat_desc换成"AREA HARVESTED")，只在每年9-11月收获季有数据。
  收获快→新豆快速流入市场→偏空；收获慢(比如秋雨连绵导致收割延误)→偏多。
  同样没有历史同期均值做基准，置信度低于其他指标。

1月合约的综合评分上限也从12变成14(南美综合信号+1，收获进度+1)。

**5月合约新增了2个专属指标**：
- **美豆播种进度**：复用已有的NASS Quick Stats API(跟美豆优良率同一个接口)，
  只是统计类别换成"AREA PLANTED"(播种进度)而不是"CONDITION"(生长状况)。
  只在每年4-6月播种季有数据。⚠️没有历史同期均值做对比基准，只能用周环比推
  进度快慢做粗略参考，置信度低于其他指标。
- **巴西雷亚尔汇率(USD/BRL)**：复用已有的Frankfurter API(跟人民币汇率同一个
  免费接口，无需密钥)。雷亚尔贬值→巴西农户换算成本币收入更划算→加快卖粮→
  出口供给增加→偏空；雷亚尔升值→农户惜售→偏多。**阿根廷比索因汇率波动过大，
  未被这个数据源收录，暂无法覆盖**。

这2项只在5月合约窗口显示和计入评分(其他窗口跟这2项关系不大)，跟"南美天气+产量"
是两件不同的事——不合并进同一个综合信号，各自独立投票。5月合约的综合评分上限
也相应从13变成15。

**出口销售(ESR)和供需库存(PSD/WASDE)这两块，3个合约下都会一直显示，用的是同一份数据**——
它们本质上是"连续性的市场基本面"(每周/每月持续更新)，不是按合约月份切出来的独立数据，
所以不会跟着切换合约被隐藏。但界面上会有一段跟着合约变化的说明文字，提示同样的数字
在不同窗口期该怎么解读(比如9月合约窗口，WASDE数字还是趋势预估；1月合约窗口，
已经反映真实收获数据，确定性高得多)。

大商所豆粕期货真正的主力合约只有3个：1月/5月/9月（其余月份也挂牌但交易不活跃）。
这3个合约对应的基本面关注重点完全不同：

```
9月合约(现在这个窗口期) → 美豆生长关键期(6-8月)天气 → 页面默认配置就是围绕这个设计的
```

### 已确认修复的两个真实bug（感谢实际部署反馈）

**① 干旱监测：aoi参数用错了类型**
官方文档（droughtmonitor.unl.edu/DmData/DataDownload/WebServiceInfo.aspx）明确写着：
州级查询的aoi参数必须用"两位数FIPS代码"，不是两字母邮政缩写。
之前代码用了`aoi=IA`，正确应该是`aoi=19`（Iowa=19, Illinois=17, Minnesota=27）。
这也是为什么之前返回HTTP 200但内容是空数组`[]`——请求格式合法，只是查无此州。已修复。

**② 供需库存：接口返回数字ID不是字符串名称**
实际部署后发现，接口返回的每一行数据长这样：
`{"attributeId":7, "unitId":8, "value":74843, ...}`
根本没有"Ending Stocks"这种字符串字段，只有数字编号。
现在代码会额外查一次"属性名称对照表"接口，把数字ID翻译成人类可读的名称。
这个对照表接口的确切路径没有100%把握（USDA没给出完整交互式文档），
如果这个也查不到，会在诊断信息里明确说明，不会静默失败。

## 粘贴解析的工作原理（开机率/库存/基差/到港预报/猪粮比/能繁母猪/进口量/肉鸡养殖利润/豆菜粕价差）

这7个指标背后是商业数据服务(汇易/mysteel)或政府网页表格，没有公开API。
之前尝试过让脚本自动调用AI(Groq+Tavily)联网搜索，但实测发现：AI经常把
过期数据或者不相关的数字（比如价格表格里的某个数）误判成目标指标——
这不是换个AI模型能解决的问题，因为根源是"公开网络上搜不到干净权威的数据源"，
AI只能从搜到的内容里提取，搜到的东西本身不可靠，再强的AI也无能为力。

现在改成更简单可靠的流程：

```
① 点击"复制提示词"按钮 → 提示词自动复制到剪贴板
② 粘贴到你信任的任意AI对话框（DeepSeek/豆包/通义千问/ChatGPT都行）
③ 看一眼AI给出的表格，人工确认数据是否合理
④ 把AI的完整回答复制粘贴回网页的文本框
⑤ 点击"解析并填充" → 本地正则解析每一行，识别指标/数值/日期/来源
```

解析是纯本地文本处理，不联网、不调用任何AI服务。支持识别：
"约1100万吨"这种带修饰词的表述、"3.88:1"这种比值格式、"-182"这种负数、
"2026年6月末"这种月末表述会自动换算成当月最后一天。
识别不到的字段会保持原值不受影响，你也可以随时手动编辑覆盖解析出来的数值。

### 前端K线图：改用专业图表库(不是手写SVG)

**用户反馈第一版K线图(手写SVG，只有MA20/MA60，不能缩放、看不到具体数值)后，
认识到手写SVG从一开始就不是做K线图的正确工具**——K线图天然需要"缩放看细节"
"悬停/点击看具体开高低收数值"这些交互能力，硬用静态SVG图片实现这些等于重新
发明轮子，而且做得不会好。

改用 [TradingView Lightweight Charts](https://tradingview.github.io/lightweight-charts/)：
- 免费开源(Apache 2.0协议)，只有35KB，专门为K线图设计
- 内置双指缩放、拖动平移、十字光标显示具体数值——不需要自己写这些交互逻辑
- 通过CDN加载(`<script src="https://unpkg.com/lightweight-charts/...">`)，不需要
  npm install，符合这个项目"单文件HTML"的整体架构
- 这是整个项目**第一次引入前端外部库依赖**(之前所有图表都是手写SVG)。
  之所以在这里破例，是因为K线图这个场景的复杂度(海量数据点+缩放+悬浮提示)
  跟其他简单图表(比如12州对比条形图、仪表盘指针)完全不是一个量级——
  简单图表继续手写SVG就够了，不需要为了"架构一致性"牺牲K线图该有的可用性

**均线也从只有MA20/MA60扩展到MA5/MA10/MA20/MA40/MA60**这个更完整的常用组合，
数据量不够某条均线的长度时会自动跳过(比如只有40根数据时不画MA60，避免整条空线)。

**新增MACD(12,26,9)副图**，独立的图表面板(柱状图+DIF/DEA双线)放在主K线图下方，
时间轴双向同步(缩放/拖动任意一个图，另一个跟着动)。DIF/DEA计算用标准EMA(指数
移动平均，不是简单移动平均，近期数据权重更高)，柱状图=(DIF-DEA)×2(按中国习惯
乘以2)。同时会自动侦测**最近一次金叉/死叉**(DIF上穿/下穿DEA)，用文字总结显示
"最近一次金叉：2026-06-15(3个交易日前)"这样的结论，不用自己盯着图找。

⚠️ 按Lightweight Charts的开源协议要求，图表上会保留TradingView的版权标识，
没有关闭这个默认行为。

**修了一个真实bug：小时线图表之前完全不显示**。原因：小时线图表容器包在默认
收起的`<details>`折叠区块里，之前代码在页面刚加载时就立刻创建图表，但那时候
`<details>`还是收起状态，容器的宽高都是0——图表其实"建出来了"，只是尺寸是0，
完全看不见，而且之后展开也不会自动修复(图表库只在创建那一刻读取容器尺寸，
不会持续监听`<details>`的开合状态)。改成延迟初始化：只在用户真正点开这个
折叠区块的时候才创建图表(这时候容器已经是正常尺寸了)，且只初始化一次，
重复展开/收起不会重复建图表。

**修完上面这个之后又发现第二个bug：图表框架/网格线正常显示，但蜡烛完全看不见**。
原因：小时线的时间字段是"2026-07-13 14:15:00"这种带时分秒的字符串，日线的
"2026-07-13"这种纯日期字符串Lightweight Charts能直接认，但带时间部分的必须
转成UNIX时间戳(数字)才行——之前直接把字符串传进去，图表本身能正常创建和响应
鼠标交互(所以框架/十字光标看起来"有反应")，但蜡烛数据解析失败，完全不显示。
⚠️这个时间字符串是北京时间(DCE数据源)，转换时特别注意不能直接当UTC解析
(会有8小时误差)，需要显式指定+08:00时区偏移。


**新增指标(用户提供了一份完整的盘口/技术指标清单，逐项分析了哪些能做/不能做后实现)**：
- **完整统计列**：今开/今高/今低/昨收/昨结(结算价，之前查过akshare有这个字段但代码
  一直没提取)/持仓量/日增仓，都是K线数据里本来就有(或容易算出来)的字段，之前没有
  显示出来
- **成交量副图**：柱状图(红涨绿跌同一套配色) + MA10(金)/MA20(蓝)均量线
- **RSI(14)副图**：标准Wilder平滑法(不是简单移动平均)，70/30两条参考线标出超买/
  超卖区间，用经典Wilder教科书案例(公认基准RSI≈70.46)验证过精确度
- 小时线也补上了MACD(之前只有日线有)

**诚实说明清单里其他指标的可行性**(不是照单全收，逐项分析过)：
- 卖价/卖量、买价/买量(盘口深度)、外盘/内盘(逐笔成交方向) → 免费数据源拿不到，
  需要付费实时行情或交易所会员权限，这几项没有做
- 停板(涨跌停板)、杠杆(保证金比例) → 需要先查证DCE当前的具体规则数字，暂缓
- 分时图(今日分钟级价格线/均价线/分时MACD) → 技术上可行(akshare支持1/5分钟数据)，
  但这是全新的数据类型(当日tick级)，且更偏短线/日内交易场景，跟用户的中长期
  交易风格关联度较低，暂未实现

## 历史基本面数据：fetch_historical_fundamentals.py（10年，2016至今）

**真正找到播种/收获进度的根因了(第三次修复)**。用户实测8/10数据源完美成功

### 跨品种验证：不只测豆粕，同时测豆油、豆二(进口大豆)

现在对`SYMBOLS_TO_TEST`里每个品种都跑一遍。★某个品种数据抓取失败(比如

**已实现8个纯技术面策略**（都用固定的止损2%/止盈4%，即2:1盈亏比，符合用户

**用户真实10年数据验证了新增的4个策略**：布林带突破36.6%(PF1.15,+28%)、
唐奇安通道37.4%(PF1.20,+48%)、KD随机指标反转40.1%(PF1.34,+72%)、量能确认

8个策略，其中一个特别突出本身要打折扣看(多重比较问题)。用二项分布检定，
KD单独看p值0.056，离常规0.05门槛只差一点点但还没跨过；用Bonferroni校正
(测8个策略门槛要收紧到0.05/8≈0.00625)后，8个策略没有一个真正跨过统计
显著的门槛。这是加入下面"样本外验证"机制的直接原因。

**样本外验证(out-of-sample validation)**：把全部数据切成"样本内"(前70%，
较早)和"样本外"(后30%，较晚，完全没被用来挑选/评估过策略)两段，分别独立
跑一遍全部策略。这是检验"某个策略回测数字特别好看，到底是真的有效，还是
测了多个策略里刚好挑出最好看那个"最直接的办法——如果样本内表现好、样本外
也保持接近的表现，才是站得住脚的证据；如果样本外明显"打回原形"(掉回33.33%
损益两平线附近甚至更差)，说明样本内的好看数字更可能只是巧合。`split_bars_
in_out_sample()`用index切分(不是具体日期)，因为bars本来就按时间排好序，
效果等价但更简单；样本外这一段的信号生成、交易模拟完全只用样本外自己的
K线数据，不会"偷看"样本内的信息。

★样本外验证也不是万能药——样本外时间段本身也只是历史上的某一段特定时期，
一致不代表未来一定还会一致，只是比"没做过这个检查"多一层交叉核对。

**用户真实数据跑出的样本外验证结果，比预期更有信息量**：8个策略里有6个
样本外胜率比样本内高(平均+7.3个百分点，排除样本太小的量能确认策略)——
这个"几乎所有策略不分机制都往上走"的规律性，更像是2023-2026这段时间
本身比2016-2023更适合方向性/趋势类技术信号，不是某个策略真的更聪明。
更关键的是排名对照：**KD从样本内排名第1(42.3%)掉到样本外排名第6(38.7%，
反而低于MACD/MA交叉/MACD+RSI/布林带/唐奇安)**；MA5/MA20交叉则反过来，
从样本内倒数第2(28.8%)冲到样本外第1(48.6%)——这种完全颠倒的排名变化，
是"雑讯"的标志，不是"这个策略真的有稳定优势"的证据。这次验证没有把
"哪个策略最好"这个问题解决掉，反而进一步说明目前测过的8个策略，没有一个
拿得出跨越两个时期都站得住脚的证据。

### MACD定方向+KD找时机+量能确认(第9个策略，按逻辑设计，不是挑数字凑的)

用户在看过上面的结果后，明确要求"按逻辑设计"而不是"挑哪个历史数字好看"
去组合策略——这个区分很重要：直接把"MA交叉样本外48.6%"、"KD样本内42.3%"
这些已经被证明不稳定的数字背后的参数拼起来，本质上是在同一份数据上做
第9次拟合，只会让过拟合更严重，不会更好。

改用"每个指标各自负责什么角色"的逻辑设计，独立于回测结果：
```
MACD负责判断趋势大方向：DIF>DEA=多头环境，DIF<DEA=空头环境
                     (看当下所处的趋势状态，不是"金叉死叉那个瞬间")
KD负责在这个趋势环境内找进场时机：多头环境下，KD从超卖区向上穿越
                     (逢低找买点，顺着大方向找相对便宜的入场点，不是逆势摸底)；
                     空头环境反过来(逢高找空点)
成交量负责确认这次转折有真实资金参与：用比较温和的1.2倍(不是2倍)，
                     因为已经叠加了MACD+KD两个条件，成交量只需要做轻度确认
```
三个条件必须同时满足才触发，任何一个不满足都不算数。

**这是第9个在同一份数据上测的假设**：前8个已经显示出多重比较的风险(KD
p值0.056没跨过显著门槛)，这个组合哪怕回测数字好看，也该比前8个更谨慎
看待——脚本运行结束时会印出这条提醒，不会让人误以为"又找到一个好策略"。

**测试构造说明**：验证这个函数用了"加速上涨/下跌的收盘价路径 + 单日插入
极端上/下影线"的技巧——只改某一天的high或low，不改close，这样能在完全
不影响MACD(只看收盘价)的前提下，单独把KD拉向超买或超卖区，让"MACD趋势"
和"KD时机"两个独立信号可控地对齐到同一天，具体验证插入幅度是反复试出来
的，不是凭空构造。

**交易模拟的关键设计**：信号在第N天触发时，从第N+1天的开盘价入场(不是用
第N天的收盘价当天下单——这是很常见的回测陷阱，会制造"未卜先知"的假象)。
之后逐日检查最高价/最低价，先摸到止损线还是止盈线就按哪个平仓。

### 方案E2(第10个策略，用户提供的手册+tqsdk代码，复现前先揪出2个bug)

用户提供了一份"方案E2"策略手册(四态分类：震荡/常规多头/强势单边/空头，
用BIAS乖离率+MA10角度定状态，ATR动态止损止盈+移动止损)，附带一份tqsdk
回测代码和"10年+61,540元/样本外+58,130元"的结果。**在复现之前，先仔细看了
一遍用户给的代码，抓到2个bug**：

1. **look-ahead bias(最关键)**：原始代码用`price = close.iloc[-1]`(当天
   收盘价)生成信号，然后直接拿同一个`price`当成交价开仓——这在真实交易里
   不可能做到，收盘价只有市场收盘后才知道，那一刻已经没有时间下单成交了。
   这正是本项目一开始就确立、backtest.py其余9个策略统一遵守的"次日开盘价
   入场"原则要避免的陷阱。这个bug通常会让回测结果系统性偏乐观。
2. **仓位比例跟手册自己的表格对不上**：`_open_long`永远用2%风险、
   `_open_short`永远用1.5%，但手册的表格写的是"震荡市/强势单边用1.5%，
   常规多头/空头用2%"，是按**状态**分不是按**方向**分。这个bug不影响
   胜率/盈亏比，只影响对外报的金额，本项目的回测不模拟仓位/资金曲线
   (统一用单笔交易百分比收益衡量，见下方)，不受这个bug影响。

**复现时的处理**：`compute_bias()`(BIAS乖离率，(close-MA)/MA×100，跟RSI/
KDJ同属震荡指标但算法不同)、`compute_ma10_angle()`(MA10今天相对昨天的
变化比例)、`compute_atr()`都是新增的指标函数。`_e2_classify_and_signal()`
把四态分类+入场判断抽成一个只接受具体数值的纯函数，方便直接用手选数值
测试每个状态/边界条件——用自然价格路径不容易验证的地方(BIAS要落在
某个区间的同时，MA10角度还要同时超过阈值，这两个条件在数学上有一定的
此消彼长关系，随便一段几何级数的价格走势很难同时精确命中两者)。
`simulate_e2_strategy()`是完整的状态机模拟：次日开盘价入场(修正bug1)、
ATR动态止损止盈、移动止损(浮盈2倍ATR保本、3倍ATR跟MA10)、连续3天破MA60
强制离场。

★**状态③(强势单边)手册要求切到60分钟图找买点，这个回测管线只有日线
数据**，没法真实模拟60分钟图的择时——这里选择完全跳过状态③的开仓判断
(不用日线数据近似60分钟数据，避免制造"测过了"的假象，宁可承认这部分
没测)。

**测试过程中额外抓到一个真实的移动止损bug**：浮盈超过3倍ATR后，代码原本
只用`max(止损, MA10)`来上移止损——但快速拉升的行情里MA10经常滞后于价格，
经常比保本价(开仓价)还低，直接用MA10会让止损**反而倒退**到比保本价更差的
位置。修正成`max(止损, MA10, 开仓价)`，确保移动止损只会越移越紧，不会
因为MA10滞后而放松保护。测试15专门验证了这个修正前后的行为差异。

**交易模拟的实现方式**：因为E2用ATR动态止损止盈+移动止损，跟其余9个策略
"固定百分比止损止盈"的模式不兼容，`_run_e2_strategy()`和`_run_standard_
strategy()`把两种不同的模拟方式包装成统一接口`(bars)->(signalCount,
trades)`，让`analyze_one_symbol()`和`run_strategies_on_period()`能用
同一个循环调用全部10个策略，不需要为E2单独写一套主流程。

★E2策略跟其余9个一样，会在真实数据上按同样的流程走完：全量回测、换月日
排除后对照、样本外验证、跨品种验证——用户给的"+61,540元/+58,130元"这两个
数字，是在look-ahead bias这个bug**存在**的情况下测出来的，修正后的真实
表现，需要用户在自己的环境里跑一次这个脚本才知道。

### entry_timing参数：2026-07按用户实际执行计划调整了默认进场时机

用户看到修正后数字缩水，问"为什么改了就变差"——讨论后用户明确了实际
执行计划：打算在收盘前最后1-2分钟甚至30秒下单，用那个时间点的实时价格
去近似收盘价。这跟最初的look-ahead bias不是一回事：最初的问题是"用只有
事后才能知道的价格去指挥事前的下单决策"，这件事在时间上不可能做到；
"收盘前最后一段时间的实时价格"，是那个当下就能看到、也能拿去下单成交的，
不是事后才知道的，用收盘价去近似这个实时价格是合理的简化(前提是价格在
最后这段时间通常不会剧烈跳动，对流动性尚可的豆粕是合理假设，但不是零
风险的近似)。

出场(止损/止盈/移动止损/连续3天破MA60强制离场)全程都是盘中触价即时出场，
用户已经确认这是实际打算的监控方式(盘中随时盯着，一触价位就立刻出场，
不等到收盘前)，这部分逻辑完全没有变过，也是本来就没有look-ahead bias
问题的地方。

★这次修改entry_timing的循环边界条件时，第一次写的代码有一个运算优先级
bug(`while i < n if entry_timing == "close" else n - 1`会被Python解析成
`(i<n) if ... else (n-1)`，后半段变成一个数字而不是布尔值)——这个在跑
测试前就用手算验证抓到了，改成先算出`loop_bound`变量再判断。原本"次日
开盘价入场"的测试案例(entry_idx固定在i+1)全部要针对新的默认时机(entry_
idx等于信号当天i)重新设计验证场景，同时保留了`entry_timing="next_open"`
的测试作为对照，确认两种假设各自都正确。

### entry_timing的三种模式：从"哪个更保守"到"哪个技术上正确"

用户问"你说数据源方法论一样，那为什么回测结果还是不一样"，逼着重新回去
看用户原始tqsdk代码的`wait_update()`/`is_changing()`循环——猜测(后来证实)
`self.api.is_changing(self.klines)`检查的是"整个K线序列有没有变"，不是
只在新K线生成时才触发，而`get_kline_serial`拿到的"最后一根K线"在实时行情
下会随着每一笔成交持续更新。写了3版诊断脚本让用户在自己的tqsdk环境跑：
v1直接用`df.index[-1]`当"日期"分组，结果是个bug(那其实是500根K线滚动
窗口里的位置编号，不是日期)；v2改用K线真正的时间戳(`tafunc.time_to_
datetime(df["datetime"])`)分组，发现97.8%的交易日精确触发2次(不是随机
多次)；v3进一步打印完整OHLC，证实了这2次分别是"刚开盘、还在成形的K线"
(open=high=low=close=开盘价)和"收盘确定的完整K线"——这个模式在45个交易日
里44个都符合，证据相当扎实。

`compute_open_phase_indicators()`用O(1)的调整量算出"开盘价冒充收盘价"
那一刻的指标值，不需要重新跑一遍整个滚动窗口(公式是`MA_open[i] = MA[i]
+ (开盘价-收盘价)/周期`这种简单代数，ATR同理用True Range的调整量，BIAS
则是从调整后的MA24反推)——已经用"直接把当天数据替换成开盘价、重新算一遍
整个指标"的方式交叉验证过，数值精确一致。`entry_timing="open_then_close"`
把这个机制接进`simulate_e2_strategy()`和`simulate_v1_strategy()`，一度
是默认值。

**后来用户提供的一份TqSdk教程材料，把这件事讲得更清楚了**：判断"新K线
生成"的标准做法是检查`is_changing(klines.iloc[-1],"datetime")`，此时
`klines.iloc[-1]`才是刚收盘的那根、`klines.iloc[-2]`才是上一根——教程
原话是"很多新手用`iloc[-1].close`发信号，相当于用了未定稿的价格，这是
常见bug"。用户原始代码写的`is_changing(self.klines)`(检查整个序列，不是
专门检查最后一根的datetime)，正好对应这个被明确点名的常见bug，也正好
解释了诊断脚本测出来的"每天触发两次"现象——不是巧合，是这个bug的直接
后果。这意味着`"close"`模式(只在真正收盘确定后检查)不是三种同样合理的
假设里相对保守的那个，是**技术上唯一正确**的默认值，`entry_timing`因此
改回默认`"close"`。

三种模式现在都保留，方便互相对照，但语义上不再是平级的三选一：
- `"close"`(**默认值**，技术上正确的做法)：只在信号当天K线真正收盘确定
  后检查一次，用真实收盘价——对应"收盘前最后一段时间下单"这个用户实际
  执行计划，也是TqSdk教程里明确教的标准写法。
- `"open_then_close"`：复现原始代码`is_changing(self.klines)`这个已被
  证实的常见bug的实际效果(每天先用开盘价冒充收盘价检查一次，没触发再用
  真正收盘价检查一次)，保留下来是为了理解原始(带这个bug)数字从哪里来，
  不代表这是应该沿用的行为。
- `"next_open"`：用信号次日的开盘价入场，如果没办法在收盘前那个窗口真的
  下单成交(比如手动交易、下单有延迟)，这个假设最保守，保留下来方便对照。

**三个诚实的限制，报告里也会显示**：
1. **连续合约是简单拼接、没有平滑处理**——每次主力合约切换(比如从M2601换到
   M2605)，新旧合约收盘价不一定相等，可能出现"价格跳空"，这不是真实市场波动，
   是数据拼接的artifact。脚本会自动标记疑似换月日(单日涨跌幅超过6%)，并且
   额外计算一次"排除这些日期附近交易后"胜率有没有明显变化，方便交叉核对。
2. **只回测了纯技术面策略**。基本面数据(USDA供需/天气等)在`backtest.py`
   这个脚本运行的当下，没有历史快照可以回测——但`fetch_historical_fundamentals.py`
   补上了这块(见下一节`backtest_fundamental.py`)，只是这两个脚本仍然是分开的。
3. **回测的是过去，不是对未来的保证**。哪怕这4个策略里某一个历史胜率数字
   好看，也不代表未来还会这样——这是回测方法本身的局限，不是这个脚本
   做得不够好。

### 2026-07修正一个真实的bug：MA60反向计数器不该"只在持仓期间才累加"

用户拿一份"close模式修正版"的tqsdk脚本(改用`is_changing(klines.iloc[-1],
"datetime")`标准写法、用`iloc[-2]`取真正收盘确定的那天)在自己的环境独立
验证`+70.22%/盈亏比1.42`这个数字，结果差距很大(137笔/胜率27.7%/盈亏比
3.31，不是预期的241笔/41.5%/1.42)。追查后发现：`backtest.py`里"连续
6天(E2是3天)偏离MA60"这个强制离场计数器，被实现成"只在已经持仓时才
累加"(`if position is not None:`包住了计数器更新那一行)——但用户原始
代码里，这个计数器不管有没有持仓、每天都在累加，只有仓位关闭时才清零。

这不是环境差异或者数据源问题，是我自己重建这个策略逻辑时的一个真实
假设错误——我把这条规则实现成"从这笔仓位开仓算起，连续几天"，但用户
原始设计其实是"不管有没有仓位，价格连续偏离几天"，这两者在"开仓前价格
已经偏离好几天"这种情况下会有明显差异：修正前的版本会让计数器在开仓那
一刻"重新起算"，修正后的版本会让计数器保留开仓前已经累积的天数，导致
不少仓位在刚开仓不久就被这条规则强制平仓，拉低了胜率、减少了能走完
完整止损/止盈流程的交易数。

`simulate_e2_strategy()`和`simulate_v1_strategy()`都已经修正：两个方向
(跌破/站上MA60)分别用独立的计数器(`days_below_ma60`/`days_above_ma60`)，
每天无条件更新，不再包在"有没有持仓"的判断里；只有当"这个方向的计数器
达到门槛、且当前确实持有对应方向的仓位"时，才触发强制离场。测试案例
也相应更新，明确验证了"入场当天如果本身就已经满足偏离条件，这一天就该
算作streak的第1天"这个修正后的行为。

## optimize_e2.py：豆粕专属的方案E2参数搜索(严格训练/验证分离)

用户在看到修正look-ahead bias后E2策略数字缩水(10年+61.5%/胜率42.2%/盈亏比

出来的参数很可能只是精确拟合了这份数据本身的噪声，尤其是跨品种验证已经
显示E2策略只在豆粕上样本内外都稳定盈利(豆油/豆二不稳定甚至方向相反)，

"运气好"被误判成参数更优)，按盈亏比排序后**只选1组**表现最好的，拿去
验证段跑**一次**——不管验证段结果好不好看都如实报告，不会因为不满意就
回头换参数重试(`grid_search_e2_params()`/`_rank_param_results()`)。

★这次搜索范围只覆盖3个参数，没有搜索状态①自己的止损止盈倍数、也没有
搜索ATR/BIAS的计算周期；就算严格遵守训练/验证分离的纪律，10年总共177笔
完整交易(默认参数)，调参段只有100多笔，这个样本量本身找到的"最优参数"
仍然有相当概率只是运气，这个局限没办法通过更严谨的流程完全消除，只能

**用法**：`python3 optimize_e2.py`(独立脚本，不影响`backtest.py`的默认
参数，如果验证段结果支持"确实更好"，需要手动把选中的参数更新到
`backtest.py`里`simulate_e2_strategy()`的默认值)。

### V1策略(第11个策略，用户提供，在E2的框架上新增"大行情模式")

跟MA5(这一级是普通模式没有的)。`_v1_is_big_trend()`/`_v1_classify_and_
signal()`把识别逻辑和入场判断抽成纯函数，方便手选数值测试；`simulate_
v1_strategy()`是完整状态机，用独立的移动止损分支处理大行情(1.5/3/5倍
ATR三级)和普通模式(2/3倍ATR两级)。

★状态③这次有了日线就能算的入场路径(MA5或MA10回踩)，不用再像E2那样整体
跳过——但用户代码里另外还有一段"切60分钟图做确认"的补充入场路径，因为
需要小时线数据，本回测管线依然跳过这部分(不影响日线路径的测试)。

★测试里专门验证了大行情模式的移动止损确实跟到了MA5这一级：构造一段
加速上涨后回落的价格路径，验证最终出场价精确等于"出场前一天"的MA5值，
不是停在保本价或跟MA10那一级——这是抓"移动止损分支写错、卡在中间某一级"
这类bug最直接的办法。

★这份用户材料里"V1.0→V2.0业绩总结"那张表，显示同一策略反复修改后总收益
跳了4.4倍——这个"越改越好"的叙事，跟E2手册本身的来历有点像，是提醒自己
"老实回测、不代入这份叙事"的信号，不代表这版一定更好。这里只负责修复
明确的bug(look-ahead bias)、忠实复现用户给出的这版参数，不代入自己的
判断去"进一步调整"策略逻辑本身。

### 一个真实抓到的工具盲点：只看胜率差距，会漏掉"胜率接近但盈亏方向/幅度不一致"

V1策略真实跑出来的结果暴露了`analyze_one_symbol()`和`main()`里两处"一致性"
判读逻辑的共同盲点——**只比较胜率差距，没有检查盈亏比/累计收益的方向和
幅度**：

1. **样本外验证**：V1策略在豆粕上，样本内外胜率只差3.9个百分点(44.6%→
   40.7%)，旧逻辑会标成"一致性较好"——但盈亏比其实从1.5掉到1.09，累计
   收益从+56.43%掉到只剩+3.86%，衰减了九成。`_compute_oos_consistency()`
   新增一个检查：样本内本来是盈利的(盈亏比>1)，样本外的盈亏比掉到样本内
   的75%以下，就不能只因为胜率接近而说"一致"，改标成"胜率接近但盈亏比
   明显衰减"。
2. **跨品种对照**：V1策略在豆粕/豆油/豆二上的胜率差距只有5.7个百分点
   (旧逻辑会标"表现接近")，但豆油的累计盈亏是负的(-24.46%)，豆粕/豆二
   是正的——胜率接近，赚亏方向却不一样。`_compute_cross_commodity_note()`
   新增"是否所有品种盈亏方向一致"的检查，不一致就明确标出来，不跟胜率
   差距的判断互相覆盖。

这两个判读函数都抽成了纯函数，方便直接用手造的数值(包括V1策略这次跑出来
的真实数字)测试，也方便以后继续加别的判读维度。★这不是说V1策略"不好"——
方向、赢面依然存在，只是"一致性较好"这个标签，现在必须同时满足胜率接近
"和"盈亏比/方向不明显恶化"两个条件才会打出来，比原来更诚实。

## backtest_fundamental.py：技术面+基本面组合策略回测



`fetch_historical_fundamentals.py`把10年历史基本面数据收集齐了之后，这个脚本
负责把它跟`backtest.py`用的价格数据合并，测试"技术+基本面组合"策略。

**用法**：先跑过`fetch_historical_fundamentals.py`生成`historical_fundamentals.json`
(要跟本脚本放在同一个目录下)，然后`python3 backtest_fundamental.py`

**核心机制——"发布延迟"(publication lag)感知，这是避免look-ahead bias最关键的部分**：

USDA/USDM报告"as of"的日期，跟这份报告真正被市场知道(发布)的日期，中间有
延迟，且不同数据源延迟天数不一样。如果直接拿"as of"日期去对齐交易日，
等于让回测在信号还没公布之前就"看到"了它。已查证(有搜索来源)的实际发布延迟：

```
美国干旱监测(US Drought Monitor)    数据反映每周二状态 → 实际每周四发布   延迟2天
NASS作物周报(播种/收获进度、优良率)  数据反映每周日状态 → 实际每周一下午发布 延迟1天
USDA FAS出口销售周报(ESR)           数据反映当周四结束 → 实际下周四早上8:30发布 延迟7天(最容易被低估)
天气数据                            视为no meaningful delay，保守起见仍加1天缓冲
```

`build_as_of_lookup()`函数对任意交易日，只返回"在这个交易日当天，市场实际
能看到的最新一笔基本面数值"，而不是这笔数据本身反映的那个日期的值。

**目前实现的3个基本面信号**(都基于经过发布延迟处理后的数据)：
1. **干旱恶化**：美国干旱监测D2+比例，在生长关键期(默认6-8月)环比跳升超过阈值 → 供给端利多
2. **优良率下滑**：美豆优良率(%good+excellent)环比下降超过阈值 → 供给端利多
3. **出口销售激增/骤减**：当周出口销售相比过去4周均值的比例，明显偏高/偏低 → 需求端利多/利空

**没有纳入的信号**：PSD供需数据(usPsd/brazilPsd/argentinaPsd)。PSD数据在
一年内会随着每月WASDE报告持续修正，但`fetch_historical_fundamentals.py`
抓到的是"查询当下的最新/最终数字"，不是"当时那个时间点实际公布的数字"。
拿这个事后已知的最终数字去回测更早的交易日，会是隐蔽但严重的look-ahead
bias。要正确处理需要抓取USDA历史WASDE报告的"当期原始数字"(vintage data)，
这是完全不同、工作量大得多的另一个任务，这次先不做，避免在没把握正确
处理的情况下硬凑一个不可靠的信号。

### 方式1【确认过滤】：技术信号+基本面信号方向一致才保留

技术信号(MACD金叉死叉)触发后，如果±5个日历天窗口内出现同方向的基本面信号，
才保留这笔交易(基本面只作确认，不改变技术信号原本的入场时点)。

**用真实10年数据跑出来的结果**(2016-06至2026-07，2448根日K线)：这个方式
最大的问题是样本量——要求"技术信号"和"基本面信号"恰好在窗口内同时同方向
出现，本身概率就不高，MACD+干旱恶化10年里0次重叠，MACD+优良率下滑只有
4笔，MACD+出口销售只有7笔。用二项分布95%信赖区间检验就能看出这些样本
有多不可靠：

```
纯MACD对照组(n=187)：胜率34.8%，95%信赖区间[28%,42%]——区间还算窄，有参考价值
组合+优良率下滑(n=4)：胜率0.0%，95%信赖区间[0%,60%]——区间宽到几乎啥都说明不了
组合+出口销售(n=7)：胜率42.9%，95%信赖区间[10%,82%]——同样宽到没法下结论
```

样本量比较够看的纯基本面信号本身(优良率n=35、出口销售n=43)，胜率的信赖区间
也都跨过了2:1盈亏比的损益两平线(33.33%)，统计上没法把它们跟"纯粹碰运气"
分开——这个结论其实跟`backtest.py`纯技术面回测的发现是一致的：无论技术面
还是基本面，这批信号目前都没有展现出有信心的预测力。

### 方式2【仓位加权】：连续分数代替二选一的确认/不确认

方式1的核心问题是"要求同时发生"把样本砍得太少。方式2换一个思路：技术信号
照样每次都交易(样本量完全不变，用得上backtest.py四个策略全部的历史信号)，
但把3个基本面信号从"触发/不触发"的布尔值，改成连续分数——分数用固定的
"典型变动幅度"缩放(不用z-score，因为z-score要用到全部10年的标准差，等于
用未来的统计量衡量过去某一天的分数"算不算极端"，是一种隐蔽的look-ahead)。

每笔技术信号触发交易时，都能查到"当天基本面分数支不支持这个方向、支持
的程度多强"(`alignment` = 基本面分数 × 技术信号方向)，用这个一致程度去
放大/缩小这笔交易的仓位——最多放大到2倍(方向高度一致)，最多缩小到0.25倍
(基本面明显唱反调，但不会真的降到0，让"仓位加权"跟"直接不交易"变成同一
件事会让比较失去意义)；基本面没有意见(比如1-5月这几个信号都不适用的
月份)时倍数固定1.0，不产生任何偏向。

**额外算出的诊断指标比"加权总盈亏"更重要**：`alignmentPnlCorrelation`
(一致程度跟交易实际盈亏的皮尔逊相关系数)。如果这个数字明显大于0，说明
基本面分数真的在预测交易表现；如果接近0甚至为负，就算加权后总盈亏数字
好看，也很可能只是少数几笔大仓位交易碰巧赢了，不代表分数真的有效，
不该照着这个去加大实盘仓位。

**跟`backtest.py`同样的诚实原则**：历史表现不代表未来一定重现，回测结果
可能显示"没有帮助"，这本身就是有效结论，不是脚本写错了。

## 一键复制提示词更新 + 来源解析重新设计

用户给出了完整的提示词最新版本，核心变化是结尾那段指令更严格了：明确要求"数据"
必须是纯数值不能缺失、"日期"必须是年月日格式、"来源"合并成"来源及备注(文字
描述)"、新增"必须有数据列(数据列不能包含任何文字)"和"没有数据就往前找最近
日期"这两条——目的是让AI输出的表格更规整，本地解析更可靠。已经把
`PASTE_PROMPT_TEMPLATE`换成用户提供的确切文字(包括标点符号从中文逗号改成
英文逗号，逐字核对过)。

**顺带主动发现并修复了一个真实问题**：光改提示词文字不够，还测试了一下"如果
AI真的照着新提示词的要求，用markdown表格(`|`分隔)格式回复，本地解析逻辑
能不能正确处理"——测试发现数值本身能解析对，但日期(ISO格式`2026-09-22`
解析不出来，中文"年月日"格式没问题)和来源都是null。

来源解析问题更严重，查到根因：`source`字段之前是拿一份写死的机构名单
(`Mysteel`、`文华财经`、`钢联`等10个左右)去逐个比对行文字里有没有出现，
清单里没有的机构(比如用户新提示词很可能会引出的"我的钢铁网"这类)一律解析
不出来，而且这份清单本质上永远列不完，跟新提示词"来源及备注(文字描述)"这种
开放式要求已经不匹配了。改成动态抓取"数值之后剩下的文字"当作来源——但这里
还有个坑：数值后面往往紧跟着这个指标自己的单位文字(比如"68万吨"的"万吨")和
对数值的补充说明括号(比如"（全国主要油厂）")，这两层都要先跳过，剩下的才是
真正的来源，不然会把"万吨（全国主要油厂）"这种误当成来源的一部分。

16项新测试，加上原有测试集里3项因为这次重构而暴露出来的真实边界情况(数值后
紧跟单位+说明括号的组合)都修复验证过了。

## 巴西大豆播种进度(改回自动抓取)

第三项新数据源，按优先级排在压榨利润之后。这项的实现过程经历过一次结论反转，
值得完整记录下来，包括判断错误的部分。

**第一轮判断（错误）**：最初查CONAB(巴西农业部旗下国家商品供应公司，官方权威性
等同USDA)时，看到第三方库`agrobr`的PyPI描述写"默认Docker镜像包含Playwright +
Chromium(CONAB)"，据此判断这项需要浏览器自动化，于是做成了手动指标(本期+去年
同期两个输入栏位，靠AI搜索+粘贴解析获取数据)。

**用户指出这个判断有误**，理由是CONAB的周度播种进度本质是官网发布的XLSX静态
文件，只有页面完全由JS渲染、有验证码或强反爬时才需要浏览器。重新查证后发现——
**用户是对的**：直接翻了`agrobr`的源码(`conab/progresso/api.py`+`client.py`)，
确认核心逻辑是`httpx.AsyncClient`(纯HTTP客户端) + `BeautifulSoup`(从列表页
解析出最新周报的下载链接) + 直接下载解析XLSX二进制内容，源码里的元信息明确
标注数据来源为`"httpx+xlsx"`，完全不涉及Playwright/浏览器渲染。之前的判断是
把"这个库整体的默认Docker镜像包含Playwright"错误地推广到了"这一个具体函数需要
Playwright"，属于查得不够精确导致的误判。额外验证：在沙盒里实际`pip install
agrobr`(不含`[browser]`附加项)后，`pip show agrobr`确认依赖列表里没有
playwright，进一步坐实了核心功能不依赖浏览器这件事。

**于是把这项从手动指标改回自动抓取**：`fetch_brazil_planting_progress()`用
`asyncio.run()`包装调用`agrobr`的`conab.progresso_safra(cultura="Soja",
operacao="Plantio")`，返回的DataFrame按州分行(MT/PR/BR等)，取`estado=='BR'`
的全国汇总行(这个值是翻源码`parser.py`确认的：表格里出现"Estados"或"Brasil"
字样的行会被归一化成`"BR"`)。CONAB自己的报告格式本来就是"本期(`pct_semana_
atual`)+上周(`pct_semana_anterior`)+去年同期(`pct_ano_anterior`)+近五年均值
(`pct_media_5_anos`)"四个数字一起发布的，比美豆播种进度(NASS只给当周数据，
需要额外查询历史年份才能算出同比)更直接。

**一个诚实的限制说明**：本项目的开发/测试沙盒网络白名单不包含`gov.br`这个域名，
没法像NASS/CFTC那两个数据源一样，在开发环境里实测抓包确认真实响应结构——GitHub
Actions的runner网络是完全开放的，没有这个限制，但这意味着这一项的验证程度
不如NASS/CFTC那两个来得踏实。应对方式是把防御性检查写得比其他函数更详尽：DataFrame
的列缺失、找不到全国汇总行、字段值无法解析、调用过程抛出任何异常，每种情况都
单独捕获并在debug信息里给出实际看到的内容，不静默失败也不编造数据——如果
GitHub Actions第一次真实运行后发现CONAB的实际结构跟从源码读到的预期有出入，
能通过这些debug信息定位问题所在，跟这个项目一贯的"实测后修正细节"节奏一致。

判断信号沿用之前设计的逻辑：跟去年同期比，不用固定阈值(播种率是从0%累积到
100%的季节性数字，播种季初期和末期的同一个百分比意义完全不同)。播种比去年
同期慢3个百分点以上→偏多(天气不利，供给端偏紧)；快3个百分点以上→偏空(天气
配合，供给端更宽松)；差距在±3个百分点以内→中性。只在1月合约时计入综合评分
(巴西播种季在10-12月，这个窗口期国内交易最活跃的是1月合约)。

GitHub Actions workflow新增了`pip install agrobr pandas`这一步来装这个依赖。

## 美国大豆出口检验(两阶段实现，第二阶段已完成)

第六项、也是最后一项新数据源。之前判断"这类数据不够稳定"，重新查证后发现那次
放弃的其实是"拿这类数据去推算另一个指标(到港预报)"这个做法，出口检验本身作为
独立指标(衡量"实际离境的货物"，跟出口销售ESR衡量"签了多少合同"不是一回事)
值得重新尝试。

**数据源**：USDA/AMS的MyMarketNews(MARS)API——`https://marsapi.ams.usda.gov/services/v1.2`，
免费、有官方文档(HTTP Basic Auth，API key当用户名、密码留空)。这是继`USDA_API_KEY`
(FAS，用于ESR/PSD)、`NASS_API_KEY`(Crop Progress)之后的**第三套USDA相关密钥**，
需要单独在mymarketnews.ams.usda.gov注册申请，走E-Auth邮箱验证流程。

能读到的开源代码可以确认字段结构。所以`fetch_us_export_inspections()`目前
只做"探测"：扫描所有返回记录，只要**任意字段的值**里包含"soybean"字样(不区分
大小写、不预设字段名)就判定为疑似大豆记录，但**不去解析具体的数值字段**(是叫

样本放进`debug`字段里。

**真实运行暴露的bug(已修复)**：第一版硬编码了报告代码`WA_GR101`(从第三方新闻
博客"based on the WA_GR101 file"这句话反推出来的)，GitHub Actions真实跑起来后，
MARS API直接返回`{"message":"Slug Id is invalid"}`——这个代码本身就是错的，
大概率是旧版内部文件命名，不是MARS API v1.2真正用的slug_id(官方文档说slug_id
是MARS系统自己生成的，例子都是纯数字)。改成更稳健的两步设计：`_find_export_
inspections_slug()`先查`/reports`目录(所有已发布报告的清单)，按报告名称动态
搜出"Grains Inspected for Export"这份周报对应的真正slug_id(要求名称同时含
"export"和"grain"/"inspect"，避免匹配到不相关的报告)，只有唯一候选时才使用，
找到多个或零个候选都会诚实报告、把候选列表放进debug——第二步才用这个搜到的
slug_id去查实际数据。这样即使以后MARS那边调整了具体的slug编号，也不会重蹈
"硬编一个可能过期/错误的代码"这个坑。好消息是：这次的404错误证实了API key本身
是有效的(是"代码无效"不是"认证失败")，说明密钥申请和配置都是对的。

**第二轮真实运行的新发现(已加固)**：按上面这个两步设计跑了一次后，目录查询
本身确实成功了(`totalReportsInCatalog: 1051`)，但严格条件(`export`+
`grain`/`inspect`同时符合)一个都没匹配到——说明不是查询失败，是关键字假设跟
MARS实际的报告命名对不上，具体怎么对不上在没看到真实的1051份报告名称之前无法
判断。与其继续盲猜关键字组合，`_find_export_inspections_slug()`加了一层
退回逻辑：严格条件0命中时，退回到只筛`grain`这一个词的宽松搜索，把真实候选的
报告名+slug_id/slug_name摊在debug里(最多30条)，这样能直接看到MARS到底怎么
命名这份报告，不用再猜第二次、第三次；如果连`grain`都筛不到，才退到报告
"总报告数+前5条样本"这种最基本的诊断信息。

**第三轮：从真实候选清单里定案slug、完成第二阶段解析**：`grainRelatedReports`
这份真实候选清单里，`slug_id="2955"`对应的`report_name`是`"Weekly Grains
Inspected For Export"`，跟AMS官网"National Grain Reports"页面上的正式报告
标题精确匹配，其余候选(Grain Transportation Report等)明显不相关。把这个slug
硬编进`EXPORT_INSPECTIONS_SLUG`常量，`fetch_us_export_inspections()`现在优先
直接用这个已确认的值查询(只发1次请求，不用每次都先查一遍目录)，但保留了
"如果这个硬编值将来又失效了(重现WA_GR101那次的情况)，自动退回目录搜索"这个
备援——任何硬编标识符都要留一条自我修复的路，这是这一路修下来的教训。

数值字段名依然没有100%实测确认过具体英文key，延续"动态扫描"的思路：在定位到
的大豆记录里，找出字段名包含`quantity`/`metric_ton`/`weight`/`volume`/
`value`/`amount`/`bushel`这类常见计量词、且值本身能转成数字的字段，作为
"检验量"候选。只有唯一候选时才真正标记`available=True`展示出来；0个或多个
候选，都还是暂不展示数字，把候选摊在`debug.numericCandidates`里——宁可暂不
展示，也不展示一个可能读错字段、算错的数字。

前端现在有了对应的显示卡片(放在CFTC持仓旁边，都是"美国市场"相关数据)。这项
目前只有当周绝对数值，没有去年同期/环比这类比较基准(不像播种进度那样CONAB
自己给了同比)，所以做的是纯展示，不判断偏多偏空——没有基准硬判断方向是不
诚实的，跟CBOT价格、压榨利润一样标注"仅供参考，不计入综合评分"。详情区把
数值字段名和完整原始记录都摊出来，方便核对这个数字到底是公吨还是蒲式耳、
覆盖的是哪个具体周期。

## 国储进口大豆拍卖量(第10项手动指标)

第四项新数据源。跟CFTC/压榨利润/巴西播种进度那三项不同，这项经过实际查证后
确认没有可行的自动化路径，走手动指标这条路——但这次的过程值得记录，因为跟
巴西播种进度那次"查得不够精确就下结论"不一样，这次是真的动手试过才放弃：

```
① 直接fetch了国家粮食交易中心官网(grainmarket.com.cn)的"交易结果"/"交易公告"
   列表页，两次都确认页面主体是空的——列表内容由前端JS动态渲染，不在原始HTML里
② 用户实际用浏览器开发者工具的Network面板找到了背后的接口：
   https://www.grainmarket.com.cn/centerweb/getData，但这是一个通用的POST接口，
   不带完整参数直接请求会返回{"code":"002","message":"非法请求"}
③ 双方决定不再继续深挖这个接口的完整参数结构(权衡了投入产出比)
④ 查了akshare有没有现成对接函数，没找到
```

三条路都实际试过，不是凭空判断，这次的"走手动指标"结论比巴西播种进度那次更
站得住脚。

**信号设计上有个值得说明的地方**：国储拍卖这个动作本身跟"猪粮比"那种双向阈值
指标不一样——不管成交率高低，拍卖本身几乎总是"国家主动向市场投放供给"这个
动作，性质上更接近单向的。所以没有做成"量大偏多、量小偏空"这种双向逻辑，
而是：规模达到40万吨以上(参考文华财经文章里实际报道的拍卖规模，54.3万吨被
描述为常规规模)才标记偏空；规模较小或没有拍卖时是中性——**没有拍卖不代表看多**，
只是没有额外的供给端空头催化，这个区分很重要，避免把"缺乏利空"错误地当成"利多"。

这项不分合约，任何时候填了都参与评分(不像巴西播种进度那样只在1月合约生效)，
所以三个合约的maxVotes都统一加了1(sep从13到14，may/jan从15到16)。

## 压榨利润(榨利)

第二项新数据源，按用户确认的优先级排在CFTC之后。这个不是直接抓来的数据，是算出来的——
复用豆粕日K线同一个akshare接口，把`get_current_contract_code()`加了个`prefix`参数
(默认"M"不影响原有调用)，换成"Y"(豆油)/"B"(豆二，进口大豆)去查同一个合约月份的
最新收盘价，三者代入行业标准公式。

**公式+系数确认过程**：多个独立信息源交叉确认了标准公式和系数——

```
压榨利润 = 豆粕价格×出粕率 + 豆油价格×出油率 - 大豆价格 - 加工费
进口大豆(豆二/B)：出粕率78.5%，出油率18.5%
```

这组系数最权威的来源不是某个行情网站，是**大商所豆二期货厂库交割置换的官方标准本身**
("豆粕和豆油的数量分别为黄大豆2号交割数量的78.5%和18.5%")——交割置换比例就是交易所
自己定的，比任何第三方引用都更可靠。

**诚实说明这是"毛利"不是"净利"**：公式里的"加工费"(油厂自己的加工/物流成本)没有
一个公开、权威、会随时间变化的数据源可以查，硬编一个猜测数字反而不诚实(看起来精确，
实际是瞎猜)。所以仪表盘上只算到"豆粕+豆油产出价值 − 豆二成本"这一步，不减加工费——
趋势方向(涨跌)依然有参考价值，只是绝对数值会比真实净利润更高，界面上明确标注了
"未扣加工费"，不让人误以为是精确利润数字。

**豆一(A) vs 豆二(B)**：豆一是国产大豆，主要用于食品(豆腐、豆浆)；豆二是进口大豆
(转基因)，才是国内油厂榨油的主要原料，所以压榨利润用的是豆二价格，不是豆一。

**跟着合约切换**：压榨利润是按合约月份算的(9月合约用M09/Y09/B09，以此类推)，
在`main()`里对三个合约(9/5/1月)分别算好存进`crushMargins`，前端切换合约tab时
(`selectContract()`)会跟着重新渲染对应那个合约的压榨利润，跟K线/持仓排名是
同一套"按当前选中合约刷新"的机制。

只做参考展示，不纳入综合评分——道理跟CBOT价格一样，缺加工费导致的绝对值偏差，
不适合直接拿来跟其他有明确阈值依据的指标同等对待去加减分。

### 后续补充：对美豆关税(第11项手动指标)

按优先级排最后一项(原计划"并入压榨利润的成本项")，实际做的时候发现不需要真的
把关税叠进公式里——豆二(B合约)盘面价格本身就是市场对"当前关税成本下进口大豆
值多少钱"的定价结果，公式里再加一层关税调整反而是重复计算。所以改成一个纯
资讯性的手动栏位，跟压榨利润卡片摆在一起显示，**明确不参与综合评分**——
"13%"这种关税数字本身没有清晰的双向阈值意义(不是"13%偏多、20%偏空"这种），
硬做成加减分逻辑不诚实。这项存在的价值是帮助理解"美豆对比南美豆到底贵在哪"
(呼应文华财经文章里"美豆10月盘面榨利-399元/吨...巴西10月盘面榨利-331元/吨"
这种分产地对比的分析思路)，不是给综合评分再添一个信号源。

专门写了测试验证这条核心设计：填任何关税数值(0/13/25/50/负数)，综合评分的
分数都必须跟不填时完全一致——这是这个指标"仅供参考"定位的关键保证，不是
随便说说。

## CFTC持仓报告(美国版龙虎榜)

按用户确认的优先级(CFTC > 压榨利润 > 巴西播种进度 > 国储拍卖 > 关税 > 出口检验)，
这是第一项新数据源。CFTC每周五下午发布Commitments of Traders(COT)报告，
Managed Money(基金/投机资金)这一类在CBOT豆粕合约上的净多空持仓+周变化，是美国版的
"龙虎榜"——跟大商所会员持仓排名(国内视角)是同一个概念的海外对照，直接对应用户最初
想追踪的"外资/资金动向"这个关切，只不过是从美国这边的视角。

**数据源确认过程**：CFTC通过Socrata开放数据平台(publicreporting.cftc.gov)发布，
不需要API key(CFTC官方文档原话："we are not providing tokens...As long as you are
not overusing the API, you should be able to use the API without a token.")。
COT报告分Legacy/Disaggregated/TFF三种口径，只有Disaggregated才有Managed Money这个
细分类别，数据集ID是`72hh-3qpy`——这个ID交叉核对过2个独立信息源，且实测直接抓取过
真实响应验证过字段名(`m_money_positions_long_all`/`change_in_m_money_long_all`等)。
过程中还实测发现一个字段命名的坑：swap dealer那类字段在short/spread前有双下划线
(`swap__positions_short_all`)，但m_money这类没有这个问题，字段名是规整的。

**跟大商所龙虎榜的整合**：CFTC的净持仓周变化会跟大商所会员数据一起，纳入"三方共振
面板"的外资活跃度判断——阈值1万手是根据实际观察到的持仓规模(十万手量级)估算的参考值，
不是精确校准过的统计边界。两边都有显著动作时，共振面板会同时显示两边的信息，不是
互相覆盖；只有一边显著时，单独那一边也能触发"外资活跃"提示。CFTC这个信号本身不涉及
具体机构区分(不像大商所那边能标注到底是不是高盛)，所以不会被当成"高盛专属信号"。

过程中还修了一个真实bug：Python里空列表`[]`跟`None`一样是falsy，之前的判断逻辑
用`if not data:`把"请求失败"和"查无此市场记录"这两种不同情况混在了一起报同一句
模糊错误信息，改成`if data is None:`单独判断None、`if len(data)==0:`单独判断空
列表之后，两种情况现在能给出准确、不同的诊断信息。

### 后续改进：连续增减仓 + 历史百分位

用户反馈只看"本周涨跌"不够，净多头"持续增加"、"处于历史高位"、"持续下降/转净空"
这三种情况含义完全不同，值得分开展示。这几项都需要多周历史数据才能判断，不是
只看最新一周就够——把单次请求的`$limit`从1改成156(约3年周度数据)，一次请求把
历史序列都拿回来，不需要额外发起上百次请求。

```
连续增减仓：从最新一周往回看，净持仓相邻两周的差值方向连续一致就累加，遇到
           方向反转就停(连续3周以上才展示，1-2周的"连续"噪音太大没有意义)
历史百分位：当前净持仓在回看窗口(近3年)里，比多少历史值都高(或持平)——
           ≥90%标记"历史高位，警惕反转"，≤10%标记"历史低位"，需要至少52周
           (1年)数据才计算，数据不够时明确返回None，不硬凑一个没有统计意义的数字
```

三个信号彼此独立展示，不强行合并成一句话——"本周增仓"+"已经处于历史高位"完全
可能同时成立，而且这正是最值得留意的组合(追多还是见顶信号，仪表盘不替使用者
下结论，只是把这个组合摆出来)。

## 三方共振面板

页面最顶端(合约选择下方，基本面详细评分之上)新增一个小面板，把三套原本各自
独立运作的系统合起来看：

```
技术面方向(来自K线共振摘要的bullCount/bearCount多数决)
基本面方向(来自综合评分score，跟下方详细面板同一套+3/-3阈值)
外资动向(来自龙虎榜净多头/净空头/增减仓榜单里的isForeign标记)
```

设计上遵循一个原则：**只陈述事实，不生成买卖结论**，跟技术面共振摘要的原则
一致。具体规则：

- 只要龙虎榜里出现已确认的外资独资期货公司(高盛期货/摩根大通期货/摩根士丹利
  期货/瑞银期货)，面板就会明确提示"外资活跃"，并且专门区分高盛跟其他几家——
  这个区分来自某豆粕博主的经验分享："大摩做的不是趋势跟踪"，暗示不同外资
  机构的持仓变化信号价值不同，高盛更偏方向性，其余几家可能更偏对冲/客户流
- 外资活跃时，无论技术面基本面是否同向，都会提示"参考价值可能降低"——这条
  提示转述自该博主反复强调的操作原则"外资开始搞事情时，我就不做"，不是本
  项目自己发明的判断依据
- 外资平静时，才会展示"技术面与基本面是否同向"这个判断；同向时用红/绿
  (国内习惯，红涨绿跌)高亮，不同向时中性色显示

三个输入互不依赖谁先算完：`renderKline()`算完技术面+外资动向就刷新一次，
`updateOverallAlert()`算完基本面就刷新一次，两边各自更新各自负责的部分，
不需要互相等待。

## 持仓排名(龙虎榜)

显示每个合约前20名会员的持仓排名，含外资独资期货公司标注。

**2026-09更新：彻底改用东方财富的接口，不再依赖大商所官网直连**。原本用
`akshare`的`futures_dce_position_rank`直连大商所官网，接入生产环境后稳定
报`BadZipFile`错误(大商所官网反爬拦截或格式变化，`akshare`的changelog里
这个接口也反复被"修复"过好几次，是"直接抓交易所官网文件"这类接口的通病)。

**现在这个新接口的地址、参数结构、返回字段，全部是通过浏览器F12开发者工具
实测抓包确认的**，不是看文档或猜测出来的：

```
域名：datacenter-web.eastmoney.com/api/data/v1/get
关键参数：reportName=RPT_FUTU_DAILYPOSITION(期货每日持仓)
筛选条件：SECURITY_CODE(合约代码) + TRADE_DATE(交易日) + 对应排名字段
```

有个实测发现的重要细节：**这个接口返回的不是"独立的排行榜"，是"每个会员一行，
同时列出该会员在各项指标下的排名"**——比如国泰君安可能多头持仓排第1，但空头
持仓只排第4。所以每一类"前20"都必须分开查询(各自按对应的排名字段排序)，
不能从任意一次查询结果里直接截取，不然拿到的20个会员可能是按别的指标
排出来的，跟榜单标题对不上。

**扩展到6个类别**：多头持仓、空头持仓、净多头(多单减空单)、净空头、
多头增仓(今日新增多单排名)、多头减仓——按用户明确要求，`main()`里实际抓取
的是后4类(净多头/净空头/多头增仓/多头减仓)，因为这几类最能反映"资金流向"
(谁在加仓/减仓)而不只是"存量"，对判断外资资金动向更有信号价值。`long`/`short`
(多头/空头持仓)这两类接口本身也支持，但暂不在默认抓取范围内。

**外资独资期货公司标注**：查证确认目前有4家**境内外资独资**期货公司(高盛期货、
摩根大通期货、摩根士丹利期货、瑞银期货)，且高盛期货是大商所直接会员——
如果这几家某天真的进了某个榜单前20，页面上会用🌐标记+高亮显示。要诚实说明：
**这几家不一定天天都能看到**，进不进前20取决于当天它们在这个合约上的量够不够大，
大部分时候可能根本不在榜单里，这是真实市场情况，不是数据缺失或功能故障。

另外这个接口返回JSONP格式(用回调函数名包裹JSON，不是纯JSON)，新增了
`fetch_jsonp_debug()`专门处理这种格式，同时也兼容了"万一哪天接口不带回调、
直接返回纯JSON"这种情况。

T+1性质不变(收盘后才发布当天数据)，重试往前找最近交易日的逻辑也保留。

**要澄清一下这个数据代表什么**：这是**会员(期货公司)持仓排名**，不是最终客户
排名——比如"中信期货"是经纪商名字，不代表某个具体机构自己的仓位，除非该机构
本身就是直接注册的会员。就算标注了🌐的外资公司，它们的持仓也是**该机构的全部
客户+自营盘加总**，不是"高盛自己的判断"这么简单，只是相对更接近而已。

## 美豆优良率/播种进度/收获进度：同比+五年均值

用户实测发现一个真实问题：优良率58%比上周跌2个百分点，但这只是单周噪音，
真正有意义的是"58%跟去年同期(比如61%)、跟近五年同期均值(比如62.5%)比是
明显偏低还是正常"——单看环比容易被单周波动误导，判不出真正的异常水平。

具体设计上分两点：

**同比+五年均值怎么算**：这三个都是NASS Quick Stats接口，本来就是按`year`
参数查询的，往前多查5年(现在总共6次请求：今年+前5年)，找每一年里
"离今年最新一周最近的那个周次"做对比——不要求日期完全对上(不同年份"同一个
月同一天"未必是周日，NASS的周次一般定在周日)，所以是找"最接近"而不是精确
匹配。五年均值按实际能查到的年份数取平均(比如某一年NASS临时查不到，就用
剩下4年的均值，不会因为一年缺失就让整个功能失效)。

**判断信号优先用五年均值，不再只看环比**：偏离五年均值±5个百分点以上才
判定明显偏多/偏空，五年均值缺失时(比如某次运行历史年份全部查询失败)才退回
环比阈值判断，但页面上会明确标注"⚠️置信度较低"，不假装退化路径的判断力
跟主路径一样可靠。

这套逻辑抽成了共用函数`computeProgressSignal()`，三个指标共用（方向语义碰巧
一致：数值比五年均值高→供给更宽松→偏空，数值比五年均值低→偏多）。

其余基本面指标(库存型/流量型)要不要套用同一个思路、CFTC持仓/压榨利润等新
数据源，下一步陆续加。

## 移动端UI精简 + 技术面共振摘要

**参考TradingView的思路：默认只显示最核心的内容，细节收起来点开才看**，
针对"现在太丑、太复杂"这个反馈做的调整：

- **MACD/RSI改成收起状态**，跟小时线一样点开才加载图表(复用同一套已验证过的
  延迟初始化模式，避免收起状态下容器宽高是0导致图表看不见的老问题)
- **统计列从9个方块精简成一行文字(今开/最高/最低) + 6个方块**，减少默认
  就占满屏幕的视觉噪音
- **新增"技术面共振摘要"卡片**：把趋势(均线排列)、RSI、MACD柱状图方向、
  金叉死叉、价格相对支撑/压力位这5项，各自独立判断偏多还是偏空，纯计数
  汇总成"N项偏多/M项偏空/K项中性"

**关于这个共振摘要要说清楚的边界**：这只是把"现在有几项指标指向哪个方向"这个
事实透明地摆出来，**不合成一个买/卖结论，也不给具体的止损止盈点位建议**——
这块跟之前讨论过的一样，具体怎么判断、在哪里进出场，还是要交给你自己结合
当下情况判断。测试里专门验证过输出内容不包含"建议买"/"建议卖"这类结论性词汇。

支撑/压力位用最近20日的最低/最高点(跟卡片上方"区间最高/最低"不是一回事——
后者是整个K线图显示范围，通常是近260日，两者时间窗口不一样，各有各的参考价值)。

## 持仓量图表 + 布林带


- **成交量图表加了持仓量线**：白色线，用独立的左侧坐标轴(跟成交量的数量级
  可能差很多，共用一个轴会互相挤压看不清)
- **布林带(20,2)**：中轨=20日均线，上/下轨=中轨±2倍标准差(标准差用总体
  标准差，布林带的标准算法惯例)，用Python独立算过基准值精确核对过JS实现
- **均线/布林带做成二选一切换**，不是同时叠加——5条均线+3条布林带一起堆在
  K线图上会很难看清楚，加了个小切换按钮，默认均线，可以点"布林带"切换看

## 技术面扩展到三个合约(9月/5月/1月)


**之前技术面(K线/MACD/RSI/成交量)只做了9月合约，现在三个合约都覆盖了**，且会
根据切换的合约tab自动显示对应数据：

- 后端`main()`现在对三个合约都分别抓日线+小时线，JSON里用月份命名key
  (`dceM09Daily`/`dceM05Daily`/`dceM01Daily`等)，不含具体年份，这样合约
  年份每年滚动时key不用跟着改
- **自动跳转当前该做的合约**：页面打开时不再写死显示9月合约，而是根据今天的
  日期，复用已有的`CONTRACT_CONTEXT.recommendedMonths`数据判断该显示哪个
  （逐月核对过，12个月无缝隙无重叠地对应到唯一一个合约）
- **验证过"往后跳"的方向**：比如8月该做1月合约，抓的必须是明年1月(如2027年
  M2701)，不能是已经过期7个月的今年1月——这个逻辑本来就是对的，但之前从没
  被真正跑过，这次补了明确的测试锁定
- **切换合约时正确清理旧图表**：LightweightCharts的图表实例如果不清理会越
  攒越多(内存泄漏+时间轴同步监听器堆积)，现在切换前会先调用`.remove()`销毁
  上一次的实例，包括切到"没有数据"的合约这种边界情况

**过程中发现并修复了一个真实的测试回归**：让合约选择跟着"今天真实日期"走之后，
有3个测试文件(涉及评分审计)因为隐含依赖"脚本加载时默认是9月合约"这个旧假设，
在9月运行时会得到不同结果——已经改成显式设置测试语境，不再受"今天实际是几月"
影响。

## 清理：移除完全冗余的南美天气后端函数

用户拿真实运行的`data/latest.json`让核对"还有哪些字段没在前端显示"，逐一比对
后发现`southAmericaWeather`这个字段虽然后端认真算了(10个产区、加权平均)，
但前端根本没读取它——`loadSaWeather()`是个完全独立的异步函数，直接在浏览器里
重新调用了一遍Open-Meteo API(一模一样的10个地点、一模一样的权重)。后端这份
纯粹是重复劳动，白白消耗GitHub Actions执行时间和`data/latest.json`文件大小，
删掉`fetch_south_america_weather()`(以及只服务于它的`SOUTH_AMERICA_LOCATIONS`/
`SOUTH_AMERICA_WEIGHTS`/`weighted_avg_custom`)不影响任何前端功能。

同一次核对里还确认了`dceM09PositionRank`等持仓排名字段"看起来没被引用"是误报——
前端用的是动态拼接的key名(`data['dce'+prefix+'PositionRank']`)，不是写死的
字面量，简单grep搜不到但实际有在用。
